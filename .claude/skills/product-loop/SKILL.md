# Product loop

How CC Bill's Phase 1 was built, made repeatable. The owner talks, tries mockups and presses **Release**. Agents do everything else, and every claim is backed by a test or a reviewer's proof.

Four stages, each a loop that ends only when its exit check passes. Never skip a stage for a "small" feature. Shrink it instead (see "Sizing").

```
1 PRODUCT   interview → drill → roast → requirements + mockup → owner tries it → feedback ↺ → LOCKED
2 TECH      dev loop + gates + environments + test data → roast ↺ → owner setup + blockers → LOCKED
3 BUILD     slices: builder → checks → independent review ↺ → gate → merge → staging   (parallel where possible)
4 RELEASE   ready-to-release check → owner presses Release → real-data validation → bug loop ↺
```

Keep one progress file (`docs/dev/progress.md`) and one tracker artifact that the owner can read on a phone. Update both at every state change.

---

## Stage 1: Product

Goal: a **locked requirements doc** and a **clickable mockup** the owner has actually tried.

1. **Interview.** Ask one question at a time, in plain words. Use the question bank in [references/interview.md](references/interview.md): who, what pain, which real cases, money and data rules, what "done" looks like, what must never happen.
2. **Drill.** For every answer, ask for the concrete case and the edge case: "show me the last time this happened", "what if it's paid twice / refunded / late / partial?" Write each case down as a numbered scenario. These scenarios later become the test plan.
3. **Roast.** Attack your own draft before the owner sees it. Look for contradictions, missing failure paths, privacy leaks, "what breaks at 10× data", and features nobody asked for. Present the roast with a recommendation for each item, and let the owner choose.
4. **Requirements + mockup.**
   - Write `docs/intent/<phase>.md`: scope, rules, acceptance criteria, out of scope.
   - Build a **single-file clickable HTML prototype** (`docs/prototype/*.html`) and publish it as an artifact the owner can open on a phone. See [references/mockup.md](references/mockup.md).
   - The mock ships with **scenario scripts** ("Try this: import October → assign Sari's payment → check her bill says Rp 0"), plus a free-play mode so the owner can check their own flow.
5. **Feedback loop.** Every owner comment becomes a mock change and a requirements change in the same turn. Re-publish to the same artifact URL. Repeat until the owner says it's final.
6. **New feature mid-way?** Run interview → drill → roast for that feature only, then update the doc and the mock. Never bolt it on silently.

**Exit:** the owner confirms "locked". Commit the doc, the prototype and the test plan (`docs/test-plan.md`, one ID per scenario, e.g. `M-03`, `P-12`). From here on, **the locked spec and prototype beat any later brief**, including your own.

## Stage 2: Tech requirements

Goal: a **locked dev loop** (`docs/intent/dev-loop.md`) and a working pipeline before any feature code. Template: [references/dev-loop-template.md](references/dev-loop-template.md).

Decide and write down:
- **Roles:** Lead (you), Builder agents, a fresh Senior reviewer, a fresh Security reviewer. Reviewers never edit code. Builders never review their own work.
- **Gates:** zero-token tools first (types, lint, unit tests with per-folder coverage thresholds, mutation testing on money and logic cores, e2e). Then the review gate: a commit status that passes only on approval markers for the exact head SHA.
- **Environments:** staging deploys automatically on every merge; production changes only when the owner presses Release. Use a separate DB name and storage prefix per environment.
- **Test data:** 100% synthetic, generated by a script, byte-reproducible, with expected results. **It must mirror the shape of the owner's real data.** Before locking, ask the owner to report the structure: which fields and statuses they used, how payments were recorded. Or give them a script that prints **counts only** and runs on their device. The agent never opens real data. See the lessons file.
- **Slice plan:** a gate-the-deploy slice first, then fixtures, then the pipeline, then core logic, then features, then shell and look, then polish and a full scenario run.
- **Owner setup checklist** with exact click paths: branch protection with required checks, **default branch = main**, auto-merge, release environment and secret, a spend limit on the CI key, and the session permission mode (Auto). Any allow-all permission rules are the owner's explicit choice and go through security review.

Roast the plan, let the owner confirm it, then build the pipeline slices and verify each owner setting yourself where an API allows it (for example `GET /repos/{o}/{r}/rules/branches/main`).

**Exit:** the pipeline is merged, a staging deploy is verified, and every owner setup item is confirmed.

## Stage 3: Build

Run the slice loop from [references/briefs.md](references/briefs.md) (copy-paste brief templates):

1. **Brief a Builder** in an isolated worktree on `claude/slice-NN-<name>`. The brief must name the spec sections, prototype screens and test-plan IDs, and say what not to touch. Use a stronger model for money, security and migration work. Builders push and never open PRs.
2. **Lead integrates:** merge `origin/main` into the branch, run every check locally, and open the PR.
3. **Fresh reviewer, given the code and not your opinion.** Senior always; Security when the diff touches risky paths (import, AI payloads, storage, workflows, review scripts, `.claude/`). The reviewer must **prove each finding with a throwaway test**, then delete it.
4. **Fix loop:** send must-fixes plus your Lead decisions back to the same builder (SendMessage keeps its context). Re-review with the same reviewer, looking only at the delta. Make tiny fixes yourself, then still get the reviewer's confirmation.
5. **Approve:** post the marker comment for the exact head SHA. If the gate didn't pick it up, re-run it with `workflow_dispatch`. Enable auto-merge, and let GitHub merge. A Lead merge is allowed only as an owner-approved bootstrap exception while required checks are still being set up. Record it in the progress file. Never use it to get around a failing or missing check.
6. **Parallelism:** run 2–3 slices at once when their files don't overlap. Stacked branches merge their base, never rebase. Tell running builders when their base lands.
7. Update the tracker and progress file, then pick the next slice by urgency: data safety and money first, then blockers, then features, then polish.

Lead decision rules, owner questions (one at a time, with a recommended default) and flaky-test policy are in the dev-loop template. **Before accepting a builder's "deviation", check it against the locked spec.** Missing spec items go back to the builder, not into "phase 2".

## Stage 4: Release

1. **Ready to release:** every slice is merged, every test-plan ID has a passing test, the full e2e run passes on staging, and every review is green.
2. The owner presses **Release**, or says "release it" and you dispatch it. The workflow runs a real-API check on synthetic data, then staging e2e, then publishes, then a prod smoke test, then the tag. Any failure leaves production unchanged.
3. **Tell the owner honestly what is not proven:** their real data, the real AI on their documents, their phone, and human usability. Give a safe first-use path: migrate but keep the old data, use it for 1–2 cycles, then delete.
4. **Real-data bug loop:** ask for screenshots of the totals or summary screens, cropped or redacted by the owner. Don't ask for raw data. Form a hypothesis from the code. Add a **synthetic fixture with the same shape** to reproduce it. Then fix, review and release again.

## Sizing

- **New app or phase:** all four stages in full.
- **New feature:** a short interview, drill and roast; update the doc, mock and test plan; then one or a few slices through the same gates.
- **Bug fix:** reproduce it with a synthetic test, write one slice, review, release.

Never shrink the gates. Only shrink the scope.

## Operating notes

- Talk to the owner in plain words: what changed for them, what is waiting on them, and what's next. Give no internal agent ids. Keep updates short and frequent.
- Read [references/lessons.md](references/lessons.md) before Stage 2 and before the first release. It lists the traps this loop hit.
- Worked example in this repo: `docs/intent/phase-1.md`, `docs/intent/dev-loop.md`, `docs/test-plan.md`, `docs/prototype/ccbill-prototype.html`, `docs/dev/progress.md`.
